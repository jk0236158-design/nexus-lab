# 翻訳のルール (内部用語 → 公開用語)

## このルールは何のためにありますか

AI Operator Pack のドキュメントを書く時、 「専門の言葉」 を「普段の言葉」 に置き換えるための 4 つのルールです。

書く人 (Zen / Akari / Iwa / Kagami / Hoshi / Oto / Kura / Kai / jun) 全員が 同じ form で翻訳できるように、 4 つのルールにまとめました。

## ルール 1: 英語は固有名詞のみ

英語の単語は、 固有名詞 (人名、 道具の名前、 技術の名前) のときだけ使います。 動詞、 副詞、 抽象名詞は日本語に翻訳します。

| OK | NG |
|---|---|
| 「Yuino が会話から気づきを拾う」 | 「Yuino が conversation から insight を extract する」 |
| 「Aira の closed loop が回る」 → 「Aira の **ぐるぐる回る仕組み** が回る」 | 「Aira closed loop run する」 |
| 「Claude Code で setup する」 (Claude Code は固有名詞、 setup は OK 慣用語、 但し 「準備する」 が望ましい) | 「Claude Code で reify する」 |

### 翻訳されない英語 (固有名詞 + 国際用語)

- **固有名詞**: Aira / Yuino / nokaze / Zen / Kai / Knot / Claude / Codex / Gemini / Cursor
- **技術の標準語**: API / CLI / Markdown / HTML / Local Web App / SaaS / OAuth / JWT
- **道具の名前**: VitePress / shadcn / Tailwind / Hono / SQLite / lucide-react

## ルール 2: 比喩を使う

専門の概念を、 日常の物事の比喩で説明します。 「これは何に似ているか」 を考えて、 似ている日常の物事の名前を借ります。

| 専門の言葉 | 比喩の言葉 | なぜこの比喩か |
|---|---|---|
| knot | **結び目** | 糸が結ばれた点 = 大事な箇所が固定された |
| hardness | **硬さ** | 柔らかい結び目はほどける、 硬い結び目はしっかり |
| Discovery | **発見** | 新しい何かが見つかる |
| Validator | **確認役** | 過去のルールを守る |
| trace | **足跡** | 過去の動きが残った記録 |
| closed loop | **ぐるぐる回る仕組み** | 同じ場所を回り続ける形 |
| Approval Gate | **承認の関所** | 通る前に確認される場所 |
| Audit Log | **作業の足跡** | 何をしたかの記録 |
| Fail Closed | **怪しい時は止まる** | 安全か分からない時の動き |
| Reset / Forget | **全消し** | 全部消す動き |

### 比喩を使わない場合

技術の standardize された概念で、 日本語で慣用化されている用語は、 そのまま使います。

- 「ファイル」「フォルダ」「コマンド」「ボタン」「クリック」「画面」「ブラウザ」 等
- 「設定」「インストール」「アンインストール」「アップデート」 等

## ルール 3: 動詞は和語、 名詞は漢字 + ひらがな

動詞は 「動く」「見る」「書く」「使う」「作る」「変える」「壊す」「直す」 等の和語を使います。

名詞は 「気づき」「判断」「足跡」「結び目」「対処」「振り分け」 等の 漢字 + ひらがな の form を使います。

| OK | NG |
|---|---|
| 気づきの足跡 | knot trace |
| 結び目の硬さ | knot hardness |
| 確認役の働き | Validator function |
| 承認の関所 | Approval Gate |
| 作業の足跡 | Audit Log |

### カタカナの扱い

カタカナで標準化されている技術用語は OK:

- インストール / アップデート / リセット / プロジェクト / ファイル / フォルダ / ブラウザ / アプリ
- ガイド / マニュアル / チェックリスト / テンプレート / ライセンス / リポジトリ

但し、 専門の技術用語をカタカナ化しただけのもの (例: 「リファクタリング」「デプロイ」「コミット」) は、 文脈で必要なときのみ使い、 普段は日本語で説明:

| カタカナ | 日本語の form |
|---|---|
| リファクタリング | コードの整理 |
| デプロイ | 公開する |
| コミット | 保存する (git の保存) |
| プッシュ | 押し上げる (git の push) |
| プル | 引っ張る (git の pull) |
| マージ | 合体する (git の merge) |

## ルール 4: 専門用語が必要な時は (= ) で内部用語を併記

技術文書で内部用語を使う必要があるときは、 公開用語の後に (=) で内部用語を併記します。

> 「気づきの結び目 (= knot) は、 AI 研究で 『knot』 と呼ばれている小さな印です」

このルールは公開 docs の最初の 1-2 段落で使い、 以降は公開用語のみ使う、 form です。 これで、 専門の人が「内部用語」 を知ってる場合も、 4 ヶ月初心者が「公開用語」 だけで読める場合も、 両方 OK になります。

### 例: docs の最初の段落

```markdown
# 気づきの足跡 (knot trace) について

「気づきの足跡 (= knot trace)」 は、 過去にあなたが何に気づいたかを記録した、
時系列の道です。 「ある時点で『これ大事だな』と思ったこと」 が、 そのまま順番に
並んでいます。

足跡を見返すことで、 今の判断がどう作られたかが分かります。 「なぜこの方針に
なったのか」 「どこから違う方向に行こうとしているか」 を確認できます。

## 硬さ

足跡には 「硬さ」 があります。 硬い足跡は、 何度も確かめられた、 ほぼ確定の
気づきです。 柔らかい足跡は、 まだ仮説の段階です。
...
```

最初の段落で 「気づきの足跡 (= knot trace)」 と一度併記、 その後は 「足跡」 のみで通します。

## 翻訳ルール違反の検出

書いたドキュメントが翻訳ルールに従っているか、 自動でチェックする道具があります。

```bash
# 1 段落で英単語が 5 件超のとき red warn
bash scripts/vocabulary_lint.sh path/to/docs.md

# Aira / Yuino の用語混同を検出
bash scripts/naming_mixup_check.sh path/to/docs.md
```

書いた直後に上記を走らせると、 ルール違反箇所が分かります。

## 例外

以下の場合は翻訳ルールを緩めて OK です。

### 例外 1: 技術文書 (developer 向け、 Zenn / GitHub README 等)

技術文書では、 専門の言葉をそのまま使う方が読みやすい場合があります。 但し、 4 ヶ月初心者向けの場合は公開用語を使ってください。

### 例外 2: コードブロックの中

コード (TypeScript / shell / Python / yaml 等) の中の英単語、 関数名、 変数名は翻訳しません。

```typescript
// OK: コードブロック内は英語のまま
const knotTrace = await fetchKnotTrace(sessionId);
```

### 例外 3: 引用部分

第三者の発話、 公式 docs の引用、 過去の commit message の引用は、 翻訳しません。

> "Yuino is not a product that is shipped once and finished" (jun, 2026-05-08)

## 翻訳の改善 + 提案

「この翻訳、 違うと思う」 「もっといい言葉がある」 等の提案は、 GitHub issue で受け付けています。

このパックは「使いながら良くなる」 構造を持った商品です。 翻訳も、 使った人の声で良くなります。
