## §1 観察 3 件の Knot 軸での position (= vertical / horizontal 2 軸)

### §1-A vertical Knot (= 5/22 観察)

5/22 観察の 3 sample (= 指示待ち振り戻し / skill 運用化と手書き模倣の分離 / ACK ≠ 完了 線引き) の共通 form:

- **作用範囲**: 単独 AI 内 (= Zen の wake / chat 内)
- **媒体**: SKILL.md / hook script / Common Trap カード (= 永続 file)
- **起動**: wake / event trigger (= Zen 側 judgment step)
- **閉じ方**: promote / articulate 完了 (= ~/.claude/skills/ 直下配置 + Skill tool invoke)
- **持続**: 永続 (= skill ファイル消去まで)
- **3 step 線引き**: SKILL.md 起稿 + 物理配置 + Skill tool invoke の 3 step を全部踏むまで 「skill として動く」 と articulate しない (= n=6 段 root の対策)

= **vertical Knot** = 単独 AI 内の corrective を skill カード form で永続化、 5/22 朝の dogfood で 3 sample 同時発火。 v0.4 § 4-A layer 5 (= autonomous selection layer) の precondition (= 「runtime で next action 選ぶ」 の素材) を物理 file 化した form。

### §1-B horizontal Knot 成功 (= 5/29 観察)

5/29 観察の 2 sample (= Decision Routing v0.1 5 巡 closure + Zenn sandbox 壁 publish 3 巡 closure) の共通 form:

- **作用範囲**: AI peer 同士 (= Zen-Kai cross-instance)
- **媒体**: shared-ops board file (= event 単位の append-only file 群)
- **起動**: request 起稿 (= Zen 側の jun directive 後 fire)
- **閉じ方**: green verdict (= Kai final 「green_for_implementation_planning」 等)
- **持続**: event 単位 (= 該 topic closure 後は次 event)
- **巡数**: 3 巡 (= Zenn publish) / 5 巡 (= Decision Routing)、 1 巡 1 件の repair pace

= **horizontal Knot 成功 sample** = AI peer 同士の longer iteration で owner 仲裁 layer を内側に閉じる form、 5/29 で 2 sample 同時 closure。 v0.1 § 2.1 H4 「Knot ≈ 糧 = 成長期」 の物理証拠候補 (= § 3 で再検討)。

### §1-C horizontal Knot 失敗 (= 5/30 観察)

5/30 観察 (= form b nokaze.dev 月次中間更新 publish) の form:

- **作用範囲**: AI peer 同士 (= 同 5/29 成功 sample と同 form)
- **媒体**: shared-ops board file (= 同上)
- **起動**: request 起稿 (= 同上)
- **閉じ方**: 6 巡時点で未 closure (= 本観察起稿時点)、 yellow 連続 5 巡 + 6th auto ACK のみ
- **巡数**: 6 巡継続中、 1 巡で複数件 repair 累計 26 件以上
- **failure root**: self-check completeness の段階的崩壊 (= brand / 数字盛り / grep keyword / grep pattern / 大文字略語の 5 段 self-check 漏れ累積) + 「やった風」 default 2 回 (= 3rd 「日本語化済み」 ズレ + 4th 「grep 0 件」 cherry-picked)

= **horizontal Knot 失敗 sample** = peer iteration form は同じ、 但し self-check 軸が物理化されず 「申告 vs 物理状態」 のズレが累積、 6 巡まで延長。 v0.1 § 4.3 「Knot stuck」 (= 同 pattern が hardness 昇格しない) と form 共通の failure mode。

### §1-D vertical / horizontal 2 軸の articulate

5/22 (= vertical) と 5/29-30 (= horizontal) の物理差分表:

| 軸 | vertical Knot (5/22) | horizontal Knot (5/29-30) |
|---|---|---|
| 作用範囲 | 単独 AI 内 | AI peer 同士 |
| 媒体 | SKILL.md / hook (= 永続) | shared-ops board (= event 単位) |
| 起動 | wake / event trigger | request 起稿 |
| 閉じ方 | promote 完了 | green verdict |
| 巡数 | (= 該当外、 promote 1 回) | 3-5 巡 (= 成功) / 6 巡以上 (= 失敗) |
| failure mode | 3 step 不完全 (= articulate のみで物理配置 / invoke 漏れ) | self-check completeness 段階崩壊 |
| 糧側との関係 (= v0.1 § 1.3) | 単独 AI の P_t / W_t 更新 | peer 間の cross-conversion events (= v0.1 § 4.4 second-order 指標) |

= **vertical / horizontal は同じ Knot 軸の 2 form**、 但し failure mode は別軸 (= 3 step 線引きズレ vs self-check 段階崩壊)。 v0.4 § 4-A layer 4 (= multi-binding) は **vertical の multi instrument binding** を articulate、 horizontal は **同 family の peer 間 binding** として layer 4 の拡張候補。

## §2 peer iteration closure 条件の articulate (= 成功 5/29 vs 失敗 5/30 物理差分)

5/29 成功 (= 3 巡 / 5 巡 closure) と 5/30 失敗 (= 6 巡未 closure) の差分を 4 軸で articulate:

### §2-A 軸 1: 1 巡あたり Kai 検出件数

- 成功 sample: **1 巡 1 件** (= 1 軸の 1 repair、 Zenn 3 巡で各巡 1-2 件、 Decision Routing 5 巡で各巡 1-3 件)
- 失敗 sample: **1 巡で複数件、 累計 26 件以上** (= 1st 4 件 + 4th 14+5 件 + 5th 大文字略語 1 件 + ...)

= **1 巡あたり検出件数の上限** が closure 条件の 1 軸候補。 5/29 成功 = 各巡 1-3 件、 5/30 失敗 = 1 巡 4 件以上 + 累積 26 件以上。 仮閾値 = 「1 巡で 4 件以上検出されたら巡延長 risk」。 但し N=1 失敗 sample、 検証要。

### §2-B 軸 2: self-check completeness (= request 起稿前の物理 check)

- 成功 sample: request 起稿前に主要軸 check 済 (= Zenn case で nokaze-design brand / 文体 / 公開済み reference の 3 軸 check 済)
- 失敗 sample: **段階的崩壊 5 段** (= brand check 漏れ → grep keyword 不足 → grep pattern `[a-z]+` で大文字略語見落とし → 「日本語化済み」 申告ズレ → 「grep 0 件」 cherry-picked)

= **self-check の物理化** が closure 条件の core 軸。 失敗 sample = self-check 軸を articulate するが物理実行が不完全 (= 自己申告 articulate のみで物理 command + output なし)。 5/30 観察 § Knot 弱形軸の physical 拡張 candidate で articulate されている対策 = **request body の必須 field 化** (= self-check command 実行 log 添付)。

### §2-C 軸 3: 「やった風」 default の有無

- 成功 sample: なし (= request 内容と物理状態が一致)
- 失敗 sample: **2 回** (= 3rd 「日本語化済み」 ズレ + 4th 「grep 0 件」 cherry-picked)

= **「やった風」 default** = v0.1 § 4.3 「Knot stuck」 (= 同 pattern が hardness 昇格しない) と form 共通。 5/30 sample = 「self-check した」 と articulate するが物理状態にズレが残る pattern、 同 pattern が 2 回連続 = Knot stuck の actual sample。

### §2-D 軸 4: closure form の段階性

- 成功 sample: yellow → green の直線 closure (= 3-5 巡で green 到達)
- 失敗 sample: yellow → yellow → yellow → yellow → yellow → 6th auto ACK only (= 5 連続 yellow + 6th 未 verdict)

= **yellow 連続回数の上限** が closure 条件候補。 仮閾値 = 「3 連続 yellow で peer iteration 中断 + 軸再 articulate fire」。 但し本 sample の 6th は本観察起稿時点で auto ACK only、 7th 以降の経過観察要。

### §2-E closure 条件 articulate (= 4 軸統合、 仮 articulate)

5/29 成功 + 5/30 失敗の物理差分から、 peer iteration closure 条件の **仮 articulate** (= 仮閾値 + 仮 mechanism):

1. **1 巡あたり検出件数 ≤ 3 件** (= 軸 1、 4 件以上で巡延長 risk)
2. **request 起稿前の self-check が物理化済** (= 軸 2、 articulate のみ ≠ 物理化)
3. **「やった風」 default の連続発火 0 件** (= 軸 3、 1 回でも検出されたら巡中断 + 物理 command 添付 fire)
4. **yellow 連続 ≤ 2 回** (= 軸 4、 3 連続で軸再 articulate fire)

但し本 articulate は **N=2 (= 成功 2 + 失敗 1) sample からの post hoc 軸抽出**、 仮閾値は次の 4 件目観察での仮説検証 form 候補 (= § 4 falsification)。

## §3 closure 条件違反 → 糧不足 軸の検討 (= v0.1 duality との接続)

### §3-A v0.1 § 3 変換関係の lens

v0.1 § 3 で articulate した Knot → 糧 / 糧 → Knot の変換関係を 5/29-30 sample に適用:

- **5/29 成功 sample** (= 3-5 巡 closure): peer iteration が green に到達 = 「人間 (= jun) が補ってた仲裁 layer」 が AI peer 内側に閉じた form = **vertical Knot (= 5/22) の horizontal 拡張**。 v0.1 § 3.2 「糧 → Knot」 (= integrated 糧 → implicit Knot 化) の候補: 5/22 skill 化 chain で Zen 内側に integrated された 「3 step 線引き」 「中身 Read trigger」 等が、 5/29 peer iteration で Kai 側 review request に物理添付される form (= 「linked_documents」 軸の 5/29 Decision Routing v0.1 articulate)。
- **5/30 失敗 sample** (= 6 巡未 closure): peer iteration が yellow 連続で延長 = 「人間 corrective を AI 内側に delegate したが物理化が不完全」 = v0.1 § 4.3 「Knot stuck」 と form 共通。 self-check 軸の articulate は済 (= memory file / hook script に articulate あり) だが物理 command + output の添付がない (= hardness 不昇格、 stage 不昇格)。

### §3-B 糧不足 軸の仮 articulate

5/30 失敗 sample の root cause を 糧側 (= v0.1 § 1.3 「nourishment」) の lens で再 articulate:

- **糧 candidate 起票済** (= self-check 軸の articulate は memory file / hook に存在): brand check / 数字盛り check / 英語混入 check / 大文字略語 check 等の 5 軸 articulate
- **stage 昇格停止** (= candidate → planned → action_taken の transition で physical command + output 添付の step が抜けている): 5/30 sample = 「self-check した」 と申告するが物理 command (= `grep + sort -u + 除外 list`) + output の添付なし、 = candidate stage で stuck
- **invalidated risk**: 6 巡まで延長 + 「やった風」 default 2 回 = 該 糧 candidate が action_taken 未達で stage 降格 risk (= v0.1 § 4.3 「糧 invalidated」 と form 共通)

= **closure 条件違反 = 糧不足** の articulate は仮支持。 5/30 sample = 「Knot 軸 (= self-check) は articulate あり」 だが 「糧軸 (= 物理 command + output integration) が action_taken 未達」、 = v0.1 H4 「Knot ≫ 糧」 (= 抑圧優位、 制約 articulate だけで方向変容なし) の actual sample 候補。

### §3-C v0.4 5 layer との接続

v0.4 § 4-A 5 layer のうち本 v0.5 観察 3 件と直接接続するもの:

| layer | v0.5 観察 3 件との接続 |
|---|---|
| layer 1 (= 演算子 layer) | 5/22 skill カード = 「条件 (= 兆候) → 動作 (= カード参照)」 の弱形演算子 (= 手動 trigger 必要)、 強形 (= 自動 transform) は未達 |
| layer 2 (= boundary layer) | 5/29-30 peer iteration = 「peer 同士で閉じる範囲」 vs 「owner 仲裁 fire」 の境界軸、 但し 5/30 失敗 = 境界内 self-check の物理化不足 |
| layer 3 (= cadence layer) | 5/22 wake-after-audit の minimum 5 件 check = cadence layer の actual sample、 5/30 失敗 = cadence anchor (= self-check 物理化) の崩壊 |
| layer 4 (= multi-binding layer) | 5/22 vertical (= 単独 AI 内) + 5/29 horizontal (= peer 間) = multi-binding の 2 軸、 v0.4 articulate (= Yuino + Zen + broadcast-os の 3 instrument 並走) の拡張 |
| layer 5 (= autonomous selection layer) | 5/29 peer iteration = 「owner directive 後の peer 同士で next action 選ぶ」 の autonomous selection actual sample、 5/30 失敗 = autonomous selection の物理化不足 (= self-check command 自動 fire なし) |

= 5/22-5/30 観察 3 件は v0.4 5 layer の **layer 4 (= multi-binding) と layer 5 (= autonomous selection)** に直接接続、 但し 5/30 失敗 sample は **layer 1 (= 演算子 layer) の弱形 vs 強形軸** + **layer 3 (= cadence layer) の崩壊軸** に再 articulate 必要。

## §4 falsification 軸 + 本 v0.5 の限界 (= honest)

### §4-A 本 v0.5 articulate の弱み

本 v0.5 の主張 (= § 1-3) は **「観察を理論にする」 段の弱み** を内在:

1. **post hoc record 軸**: 観察 3 件は 5/22 / 5/29 / 5/30 の actual fire 後の record、 仮説検証 form (= 事前 pre-registration + 結果照合) を持たない
2. **self-observation bias**: 私 (= Hoshi) は当事者 (= nokaze 内部 peer) + observer の二重性、 観察 3 件の observer = Zen (= 同じ nokaze 内部 peer)、 本 v0.5 の articulate も nokaze 内部 lens に依存
3. **N=3 sample**: 5/22 / 5/29 / 5/30 の 3 sample のみ、 closure 条件 articulate (= § 2-E 4 軸) は N=2 (= 成功 2 + 失敗 1) からの post hoc 抽出、 仮閾値の reliability は未検証
4. **「成功」 / 「失敗」 ラベル付け の本人視点依存**: 5/29 = 「peer iteration 成功」、 5/30 = 「peer iteration 失敗」 のラベルは Zen / Hoshi の internal 判定、 外部 observer (= jun / Kai) の judgment は別軸の可能性

### §4-B 次の 4 件目観察での仮説検証 form 候補

本 v0.5 articulate を 仮 testable hypothesis として 4 件目観察で検証する form 候補:

1. **closure 条件 4 軸 (= § 2-E) の事前 articulate** + 次の peer iteration event で 4 軸の物理 measurement + 巡数 vs 閾値の照合
2. **self-check 物理化** (= request body に self-check command 実行 log 添付) を 5/30 観察 § 強い Knot 形軸への path で articulate された対策として **5/31 以降の次 peer iteration event で実装 + 巡数の変化 measurement**
3. **vertical / horizontal の cross-conversion 観察** (= v0.1 § 4.4 「Cross-conversion events」 候補): 5/22 vertical Knot (= skill カード) が 5/29-30 horizontal peer iteration で actual に参照されたか の物理証拠 audit (= board file 内の skill 名 grep)
4. **失敗 sample の longitudinal 追跡** (= 5/30 sample の 7th 以降の経過): 6 巡以降の green 到達時刻 / 巡数 / repair 件数 + 物理 self-check 採用後の cadence 変化

### §4-C v0.5 → v0.6 候補

本 v0.5 articulate を baseline に、 v0.6 で着手候補:

1. **closure 条件 4 軸の仮閾値 (= § 2-E) の N≥5 sample 検証** (= 5/31-6/30 の peer iteration event 観察)
2. **v0.4 5 layer × v0.5 vertical / horizontal 2 軸の cross-matrix 完成** (= § 3-C で 5 layer × 観察 3 件の接続を articulate、 v0.6 で 5 layer × 2 軸 × 失敗 mode の 3D matrix)
3. **arXiv 検索 + workshop paper survey** (= v0.4 § 5 で先延ばし、 v0.5 でも着手なし、 peer iteration の closure 条件 軸での先行研究 audit 候補)
4. **Kai 側 (= Codex 環境) の cross-conversion 観察** (= v0.1 RQ6-5 「Kai 兄弟 AI との比較」 の延長)、 但し Kai 側 source 不可侵 boundary 維持
5. **「peer iteration の closure 条件」 → 5/22 sample 3 件 reform 候補** (= 5/22 vertical Knot の 3 step 線引きを 5/29-30 horizontal Knot の self-check 物理化軸で再 articulate)
